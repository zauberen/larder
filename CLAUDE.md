# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Larder is a self-hosted household recipe app in Clojure. One server holds one shared recipe list, pantry, grocery list and meal plan; signed-in users manage them, visitors read published recipes (and, per a site setting, check off grocery items), and Claude reaches all four over MCP. It copies the stack, shell and styles of [Block Shipper](https://github.com/zauberen/block-shipper) (files are copied, not shared).

It is built in phases (see the spec): **1 Shell** ✅ · **2 Recipes** ✅ · **3 Ingredients and units** ✅ · **4 Web import** ✅ · **5 Pantry** ✅ · **6 Grocery** ✅ · **7 Pantry status** ✅ · **8 Made it** ✅ · **9 Meal plan** ✅ · **10 MCP with API keys** ✅ · **11 MCP with OAuth** ✅ · **12 Tandoor import** ✅. Update this file as each phase lands.

Decisions made so far: the app is named Larder (`com.larder`, `~/.larder`); Phase 3 seeds a common set of ingredients with densities via migration.

Every source file (Clojure, our JS/CSS; not `resources/public/js/vendor/`) starts with the AGPLv3 license header (`;; Larder - a household recipe, pantry and grocery list manager.`); add it to new files.

## Commands

```bash
# Run the application
clj -M:dev -m com.main

# Run all tests (kaocha, configured in tests.edn)
clj -M:test

# Run a single test namespace
clj -M:test --focus com.larder.web-test

# Check for outdated dependencies
clj -M:chk
```

To try the app without touching your real `~/.larder` and `~/larder`, point the JVM's home elsewhere: `clj -J-Duser.home=/some/tmp/dir -M:dev -m com.main` (paths starting with `~` expand from `user.home`).

## Architecture

**Entry point:** `src/com/main.clj` configures slf4j to log to `<data-root>/logs/YYYYMMDD-larder.log`, then loads and calls `com.larder/start-server`. Only `com.larder.settings` is required up front: slf4j reads its configuration when the first logger is created, and loading Jetty or `clojure.tools.logging` creates one. `start-server` pins the restart-only settings, decides whether setup is required, runs `on-startup` (create the data folder, migrate the DB) and starts Jetty.

**Nothing may touch the database at namespace load time.** Before setup there is no database (or the chosen one is elsewhere), and tests redefine the settings only inside their fixtures. E.g. the not-found route renders per request (`(route/not-found (fn [_] ...))`) because the 404 page reads the site name.

**Onboarding** (`pages/onboarding.clj`): when there is no `~/.larder`, no database file or no users, `start-server` only starts Jetty and sets `setup-required`; every request then goes to `setup-routes` (`/setup`, `POST /api/setup`, everything else redirects to `/setup`; static files still load). Setup asks for the admin account, site name, port, data folder and database path (plus advanced: upload piece size, debug), pins the chosen settings so that database is used at once, creates the data folder, writes the settings file, creates the admin, stores the site name in `global_settings`, runs the deferred startup and logs the admin in. Pages rendered before setup use `gs/default-site-name`, never the database.

**Routing** (`src/com/larder.clj`): Compojure routes with Ring middleware (keyword-params, params, static resources from `resources/public/`, cookies) plus `middleware.clj`: non-GET requests whose `Origin` doesn't match `Host`/`X-Forwarded-Host` get a 403, except `origin-exempt-paths` (`/mcp`, `/oauth/token`, `/oauth/register`, which authenticate by bearer token or client credentials); bodies over 1 MB (by Content-Length) get a 413 (upload pieces may be up to the piece size); security headers are added. Access checks live in `com.larder.auth`: `requires-user` and `requires-admin`. Handlers receive `(req user)`. Admin-only settings tabs return 404 to users; admin API endpoints return 403.

Routes so far: `/` public dashboard (`?q=`) · `/recipes/:id` published recipe · `/grocery` and `/g/:token` grocery list for visitors (per access setting) · `/media/:file` recipe images · `/login` `/logout` `/setup` · `/app` recipe list (`?q=`, `?status=`) · `/app/recipes/new` Add (choice of import or blank; `?blank=1[&source_url=]` is the editor) · `/app/recipes/:id` detail · `/app/recipes/:id/edit` · `/app/meal-plan` (`?view=week|month&date=`) · `/app/pantry` (`?q=&source=&from=&to=`) · `/app/grocery` · `/app/ingredients/review` (every recipe's unmatched lines) · `/app/ingredients/:id/edit` (dialog fragment) · `/app/grocery` · `/app/settings/:tab` (`account`, `keys`; `users` and `site` for admins) · `/mcp` MCP endpoint · `/oauth/authorize|token|register` · `/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server` (also served as `openid-configuration`) · `/api/...` htmx endpoints.

**Session management** (`api/session.clj`): manual sessions, not Ring's. On login a UUID sid is stored in the `sessions` table and sent as the `larder-session-id` cookie (HttpOnly, SameSite=Strict, `Secure` over https); sessions expire after `db/session-ttl-seconds` (30 days). The session only names the user; role and enabled flag are re-read from the DB on every request (`auth/current-user` → `users/by-username`, which only returns enabled users), so disabling or demoting someone applies at once. Removing a user deletes their sessions. Unauthenticated htmx requests get an `HX-Redirect` to `/login`. Failed logins are rate limited per address (`ratelimit.clj`: 10 per 5 minutes, then 429; keyed on `:remote-addr`, since `X-Forwarded-For` can be forged — behind a reverse proxy all clients share the proxy's address).

**Roles** (`users.clj`): `admin` and `user`. Both can do everything with recipes, pantry, grocery list and meal plan; only admins manage users (add, change role, reset password, disable/enable, remove) and site settings. You can't change your own role or disable/remove yourself, and the last enabled admin can't be demoted, disabled or removed.

**Settings** (`settings.clj`): `~/.larder` (`config-path`; EDN, read with `clojure.edn`) merged over defaults. Re-read on each `get-settings`, except `restart-keys` (port, data folder, DB path), which are pinned at startup by `pin-restart-settings!`; `pending-restart` lists saved values not yet in effect. Keys: `:listen-port` (8085, so Block Shipper's 8081 stays free), `:data-root` (`~/larder`; logs in `logs/`, later recipe images), `:sqlite-db-path` (`~/larder/larder.db`), `:upload-chunk-mb` (1), `:debug` (enables the admin-only `/api/echo`), `:library-path` (blank: `<data-root>/library`; restart-only), `:library-remote` (git address, blank for none; restart-only), `:library-commit-delay-seconds` (120). `pages/server_config.clj` renders them as a form, shared by onboarding and Settings → Site → Server configuration (`POST /api/site/config`). Site settings editable from the UI live in `global_settings` (`global_settings.clj`): `site_name`, `public_base_url` (used later for share links and OAuth metadata).

**Uploads** (`uploads.clj`): from Block Shipper. A form with `data-upload="/api/uploads"` and `data-upload-kind` (only `image` so far; `pages.recipes/upload-kinds` maps kind → size limit) has its `[data-upload-file]` sent by `main.js` (`bsUploadFile`) in pieces of `:upload-chunk-mb`: `POST /api/uploads` (filename, size, kind) returns `{id, chunkSize}`, `PUT /api/uploads/:id?offset=N` appends a piece (409 with the received count when the offset is off), then the form is submitted with the id in its `[data-upload-id]` field and the handler claims the file with `uploads/take!`. Disabling the submit button during the upload makes htmx forget which button was pressed, so main.js sends its name/value in a hidden `data-submitter` field; read button values with `u/single` in case one arrives twice. Uploads belong to the user who started them and are swept after an idle hour; one survives a form with validation errors.

**Library** (`library.clj`, `library/format.clj`, `library/git.clj`, `library/hooks.clj`): recipes and ingredients live as text files in a git repo (`s/library-path`): `recipes/<slug>.txt` (header `key: value` lines — title id status servings prep cook rating tags source image created modified — then `[Description]`, `[Ingredients]`, `[Steps]`) and `ingredients.txt` (a block per ingredient: the name unindented, then indented `id`, `dimension`, `density`, `buy: 1 kg`, `always-have: yes`, one `alias:` line each). The files are the source of truth; the recipe and ingredient tables are an index. Every write in `recipes.clj`/`ingredients.clj` runs inside `hooks/writing` (one lock shared with the sync) and reports `hooks/changed!` ({:kind :action :id :name}); `library/on-change` rewrites the recipe's file (renamed when the title's slug changes) or the whole `ingredients.txt`, and queues the change only if a file actually changed. Writes made straight with SQL (the sync, `rematch-unmatched!`, `set-line-ingredient!`) don't report: line matches aren't stored in the files, they're re-derived (manual matches add an alias). Commits wait for `:library-commit-delay-seconds` of quiet (at most 10× after the first change); `format/commit-message` collapses changes per record (add+edit → add, add+del → nothing) and writes `add(recipe): Pancakes`, or for several a grouped subject (`add(ingredient): leek, kale; edit(recipe): Soup`, counts when over 72 chars) plus one line per change. After committing, `flush!` fetches, rebases onto `origin/<branch>` (a conflict is aborted, reported and retried in 10 min; local commits stay) and, if that brought commits, runs `sync!`, then pushes. git never prompts (`GIT_TERMINAL_PROMPT=0`, ssh BatchMode) and commands time out after 120 s. `init!` (from `on-startup`): create the repo, set `origin` from the setting, commit leftovers, pull, write missing files from the database (`export-missing!`: the first start commits `init: export recipes and ingredients`), then `sync!`. `sync!` loads files into the index: ingredients by id (names freed first so renames and swaps work; ingredients missing from the file are deleted, cascading their pantry rows and grocery items; blocks without an id are inserted and get their id written back), recipes by id (unchanged files skipped by comparing with `render-recipe`; a file without an id or repeating another's is a new recipe; a recipe with no file is deleted). A file with errors is not loaded (ingredients.txt: none of it; a recipe file: that recipe keeps its database version) and the error shows in Settings → Site → Recipe library, which also has Commit (and push) now (`POST /api/site/library/commit`). Without git the files are still written. Tests start the library only in `library_test.clj` (`tu` sets a 3600 s delay and calls `library/stop!`; tests call `library/flush!`).

**Recipes** (`recipes.clj`, `pages/recipes.clj`, `pages/recipe_view.clj`): `parse-form` validates the editor (title required; servings, times and rating optional; tags comma separated and de-duplicated ignoring case; ingredient lines and steps one per line, blank lines dropped) and returns `[recipe errors]`. Every save parses and matches the ingredient lines (see Ingredients). Status changes follow `pages.recipes/next-status`: new or draft → Save draft / Publish; published → Save / Revert to draft; any other button is refused. Saving responds with the detail view and `HX-Push-Url`; delete answers with `HX-Location` back to `/app`. `recipe_view.clj` holds the cards, stars, tags and detail body shared by the app and the public pages. Drafts don't exist for visitors (`recipes/published-by-id`, 404).

**Units** (`units.clj`): canonical units (g kg oz lb · ml l tsp tbsp cup "fl oz" pint quart gallon · count units each can bunch clove package piece slice stick head sprig jar bottle bag box pinch dash), `normalize` maps spellings ("Tablespoons", "fl. oz.", "cans") to them, `convert` converts within mass and within volume (US measures), between them only with a density in g/ml, count units only to themselves; nil when impossible. `format-qty` shows ½, ⅓ etc.

**Ingredients** (`ingredients.clj`): shared records (name, dimension mass|volume|count, density, default purchase quantity/unit, always-have) with aliases. `parse-line` splits a line into quantity (mixed numbers, ½-style fractions, decimals; a range takes its larger amount), unit (a bare number is "each"; units are only looked for after a number), name and note (text after the first comma, parenthesised text, a trailing "to taste"; "1 (14 oz) can" puts the size in the note); `original_text` is always kept. `match` compares `match-key`s (lower case, punctuation removed, every word singularised) against names and aliases — strictly, no fuzzy matching. Recipe saves store quantity, unit, note and ingredient_id per line. Unmatched lines are flagged in the detail view and listed in the editor's picker (`pages.recipes/picker-section`): Use an existing ingredient (the line's name becomes an alias) or Create one (dimension guessed from the line's unit; if named differently, the line's name becomes an alias); either way `rematch-unmatched!` rematches every recipe's unmatched lines. While any line is unmatched, the recipe list shows Review ingredients (N) beside New recipe, linking to `/app/ingredients/review` (`pages.recipes/review-section`): every unmatched line of every recipe, grouped by `match-key` of the parsed name (a line without a name stands alone), each group with the same Use / Create choice applied to all its lines (`POST /api/ingredients/review/match|create` with the group's `key`). The migration seeds ~45 common ingredients with densities and aliases once (`migration/seed-ingredients!`, guarded by the `ingredients_seeded` global setting so deletions stick).

**Pantry** (`pantry.clj`, `pages/pantry.clj`): one row per purchase or manual entry (ingredient, quantity — null when unknown —, unit, added_at, source grocery|manual|mcp, added_by); stock is the sum of an ingredient's rows. `parse-amount` validates form amounts (a quantity needs a unit; a unit alone is dropped). The page has an add form (a new name creates the ingredient via `ingredients/find-or-create!`, dimension guessed from the unit, then rematches recipe lines), search (names and aliases) plus source and date filters (GET params, `hx-push-url`), in-place quantity/unit edits (inputs post on change with `hx-include "closest tr"` and get the row back), and bulk delete: row checkboxes use `form="pantry-delete"` so the table isn't inside a form. `main.js` drives selections generically: `data-select-all="NAME"` toggles checkboxes named NAME, and a `data-selection-action="NAME"` button shows while any is checked and writes its `data-confirm-template` into its form's `hx-confirm`. The table reloads on the `pantry-changed` and `ingredients-changed` events.

**Pantry status** (`status.clj`): computed per request from one `status/snapshot` (all pantry rows by ingredient plus ingredient records) — take one snapshot per request and pass it around; `recipe-statuses` gets tags for many recipes with one query. A line is `:have` (stock converts to the line's unit and covers it; always-have; or the line has no amount and there is stock), `:low` (converts, above zero, not enough), `:unknown` ("Have, amount unknown": stock without a quantity or in units that don't convert) or `:missing` (no stock, unmatched). A recipe is `:ready` (all have/unknown), `:none` (all missing), `:some`, or nil without lines. `remaining` shows stock in the unit of the oldest row with an amount. Visitors and the recipe lists see only the Pantry ready tag (`view/status-tag` with `#{:ready}`); the app detail shows every line's status, stock and a grocery button. The grocery button and Add missing to grocery list use `pages.recipes/add-line-to-grocery!`: matched lines go through `grocery/add-ingredient!` with origin `recipe` and the amount from `status/grocery-amount` (default purchase size, else the recipe amount); unmatched lines become misc items with their text (not duplicated). Add missing takes Missing and Low lines and skips ingredients already on the list.

**Made it** (`cooking.clj`, `pages/made.clj`): the recipe detail's Made it button loads the dialog (`GET /api/recipes/:id/made?servings=&entry=`) into `#modal`. It lists matched lines (`made/items`) with the amount scaled by servings cooked ÷ recipe servings, an editable quantity and unit per line (`q_<line id>`, `u_<line id>`), a Ran out checkbox (`out_<line id>`) and one Add what ran out to the grocery list checkbox (checked by default); changing servings re-renders `#made-items`. Always-have ingredients are listed without amounts; unmatched lines are only counted. `cooking/made!` deducts each amount with `deduct!` (oldest rows first, rows reaching zero deleted, rows without a quantity or in non-converting units skipped), removes every row of ran-out ingredients (`ran-out!`, overriding the arithmetic), adds them to the grocery list at their default purchase size, and writes `cook_log`. The response closes the dialog, puts the message in `#recipe-message` with an out-of-band swap and triggers `pantry-changed` (the ingredients column re-fetches itself), `grocery-changed` and `recipe-cooked`. With `entry` (from a meal plan entry) it also sets the entry's `cooked_at`.

**Meal plan** (`mealplan.clj`, `pages/mealplan.clj`): `meal_plan_entries` put a recipe on a local date (ISO string) with servings (default: the recipe's), a position within the day and `cooked_at`. Weeks start on Monday (`mp/week-start`); the month grid is whole weeks. The page has a recipe bar (published recipes A–Z with their pantry tag, filtered client-side by `data-filter-list`) and a server-rendered calendar (`#mp-calendar`, re-fetched on `recipe-cooked`) whose day cells (`#day-YYYY-MM-DD`, `data-day`) are the swap targets. `main.js` handles HTML5 drag of `[data-recipe-id]` (add) and `[data-entry-id]` (move) onto `[data-day]`, plus tap a recipe then a day, posting with `htmx.ajax`; a move answers with the new day and the old one out of band (`day-response`). Entries show the pantry tag at their scale, a servings input, Made it (`?entry=&servings=`) and remove; cooked entries are marked. Add to grocery list (`mp/add-to-grocery!` over the visible range, max two months): per ingredient, the uncooked entries' scaled amounts summed in the first line's unit, minus convertible pantry stock, minus convertible open grocery amounts; stock or listed items with an unknown amount count as covering; an ingredient whose lines lack an amount or don't convert is added once at its default purchase size unless it is in stock or listed; always-have ingredients are skipped; unmatched lines become misc items. Origin `mealplan`.

**Grocery list** (`grocery.clj`, `stores.clj`, `pages/grocery.clj`): `grocery_items` are section `grocery` (an ingredient; completing adds a pantry row) or `misc` (text; no pantry row), with an optional default amount, store and origin (manual|recipe|mealplan|mcp). `grocery/add-ingredient!` is the one way ingredients get added: an open item for the same ingredient has its amount raised when the units convert (density bridges mass/volume; an item without an amount takes the new one; a new item without an amount changes nothing), otherwise a separate item is created. Completion goes through the size dialog (`size-dialog`: prefilled from the item's amount, else the ingredient's default purchase size, else a unit for its dimension) with Confirm, Skip amount (pantry row with unknown amount) and Cancel; `grocery/complete!` claims the item with `where done_at is null` first so a double submit adds one row, and stores `pantry_item_id` so `undo!` removes that row. Completed items show in a collapsed Completed list and are deleted after 24 h (on read) or by Clear completed. Typing a new store name on an add form creates the store; items group by store within each section and have a store select and a remove button (signed-in only).

One list renderer (`grocery-list`, CTX `{:app? :token}`) and one set of endpoints (`/api/grocery/items/:id/complete` GET dialog / POST, `/undo`) serve the app page, the public tab and the share link; `pages.grocery/access` decides: signed-in users always; visitors when `grocery_access` is `open`, or `share` with a valid `t` token (sent as `hx-vals`/query param). Visitors' completions and undos are rate limited (`:grocery-public`, 120 per 10 min per address). The share token (`gs/share-token`) is 32 random bytes, created on first use, compared in constant time and regenerated from Settings → Site → Grocery list access, which also sets the level (Open adds a Grocery list tab to the public dashboard). Lists refresh on `grocery-changed` and every 30 s.

**Ingredient dialog** (`pages/ingredients.clj`): clicking a pantry row's name loads `/app/ingredients/:id/edit` into `#modal`; `main.js` opens any `dialog[data-modal]` with `showModal()` and removes it when closed (`[data-close-modal]` closes). It edits name, dimension, density, default purchase size, always-have and aliases (comma separated, replaced on save, conflicts refused); success returns an empty body with `HX-Trigger: ingredients-changed`.

**MCP** (`mcp.clj`, `mcp_tools.clj`): `POST /mcp` is Streamable HTTP answered with plain JSON — tools only, no sessions, no SSE (`GET` → 405). Single JSON-RPC messages only (batches → 400); notifications and client responses → 202 with no body; an unsupported `MCP-Protocol-Version` header → 400 (supported: 2025-11-25, 2025-06-18, 2025-03-26; `initialize` echoes a supported requested version, else the latest). Methods: `initialize`, `ping`, `tools/list`, `tools/call`. Auth is the bearer token only (cookies ignored): `mcp/authenticate` tries an API key (if `mcp_api_keys` is on), then an OAuth access token issued for this server's `/mcp` (`oauth/lookup-access-token`, if `mcp_oauth` is on), and requires the user to be enabled on every call; failures are 401 with `WWW-Authenticate: Bearer resource_metadata="<site>/.well-known/oauth-protected-resource", scope="larder"` (plus `error="invalid_token"` when a token was sent). `/mcp` is exempt from the origin check by design: no cookie is honoured there, so a cross-site or DNS-rebinding page can't act as anyone without a token. Tools (`mcp-tools/tools`: name, description, JSON Schema, `(fn [args user])` with keyword args) return maps sent as `structuredContent` plus a JSON text block; `mcp-tools/fail` raises a message that becomes `isError: true` (programming errors are logged and reported generically). Batch tools take at most 200 items and validate every item before writing any. Batch items name an ingredient by `ingredient_id` or `name` (an unknown name creates it, like the add forms). Writes record the user and source/origin `mcp` (pantry rows, grocery items incl. `add_missing_for_meal_plan`, pantry rows from `complete_grocery_item`); `mark_recipe_made` uses the dialog's default scaled amounts and `ran_out` ids or names. Ingredient review: `review_ingredients` lists every ingredient with its usage (`ingredients/usage`: recipes, lines, pantry rows, open grocery items, units used), `issues` (`ingredients/issues`: unused, needs_density, measured_differently, no_default_purchase; always-have ingredients only get unused) and the unmatched lines grouped by parsed name (`unmatched-groups`); `update_ingredients` edits a batch (only given fields; null clears; `aliases` replaces, `add_aliases` adds; names and aliases must not clash within the batch) and rematches; `merge_ingredients` folds `ids` into `into_id` with `ingredients/merge!` (lines, pantry rows, grocery items and aliases move, the old name becomes an alias, blank density/default purchase are filled from the merged one).

**API keys** (`api_keys.clj`, `pages/connect.clj`): `lk_<8-char key id>_<43-char secret>`; the row stores the key id in the clear and the SHA-256 of the whole key, compared with `MessageDigest/isEqual`; `last_used_at` is recorded; revoking sets `revoked_at`. Settings → Claude (`/app/settings/keys`, everyone) creates a key, shows it once with a `claude mcp add` command and connector instructions, lists and revokes your keys. Settings → Site (admins) has the MCP sign-in switches (`mcp_api_keys`, `mcp_oauth` global settings, on by default) and every active key with revoke.

**OAuth** (`oauth.clj`, `pages/oauth.clj`): Larder is its own authorization server for `/mcp`, one scope `larder`. The site URL (public base URL setting, else the request's scheme and host) is the issuer and `<site>/mcp` the resource. Clients: dynamic registration (`/oauth/register`, JSON; public clients only, `token_endpoint_auth_method` none; redirect URIs https or http on loopback, no fragments; unused registrations swept after a week) or client ID metadata documents (an https `client_id` with a path is fetched through `fetch/fetch`, must name itself as `client_id` exactly and have `client_name` and valid `redirect_uris`; cached a day). `/oauth/authorize` checks the client and the exact redirect URI (failures there are an error page, never a redirect), then `response_type=code`, an S256 PKCE challenge and `resource` (errors after that are redirected with `state` and `iss`); signed-out users go to `/login?next=…` (`session/safe-next` only allows local paths); the consent page names the client, the redirect host (with a warning for loopback hosts) and the metadata document host, and posts back to `/oauth/authorize` (same-origin check applies). Codes are 32 random bytes, stored hashed, single use, 60 s. `/oauth/token` (rate limited) does `authorization_code` (client, redirect URI, PKCE verifier and resource must match; replaying a used code revokes the tokens it issued) and `refresh_token` (rotation: the old pair is revoked; presenting a rotated refresh token revokes the whole family). Access tokens last 1 h, refresh 30 days; both stored as SHA-256; the user must still be enabled. Tokens are bound to the resource (`resource-matches?` accepts the `/mcp` URL or the site root, case-insensitive scheme/host, default ports, trailing slash). Settings → Claude lists and disconnects your connected apps; Settings → Site lists every connection and has the OAuth switch (off: metadata 404, authorize refuses, tokens stop working). `middleware/wrap-cors` allows any origin on `/mcp`, `/oauth/token`, `/oauth/register` and `/.well-known/*` (none use cookies) and answers preflights.

**Fetching** (`fetch.clj`): every server-side fetch of an address someone else supplies goes through `fetch/fetch`: http/https only, no credentials in the URL, every resolved address checked by `blocked-address?` (private, loopback, link-local, CGNAT, multicast, ULA, mapped/NAT64 IPv4, documentation ranges), redirects followed by hand (max 5) with each hop re-checked, body capped at 5 MB (also for downloaded images), 10 s overall deadline (run in a future). The check relies on the JVM's DNS cache so the connection reuses the checked addresses. Tests bind `fetch/*allow-private-addresses*` to fetch from a local `HttpServer`.

**Import** (`import/core.clj`, `import/web.clj`, `import/tandoor.clj`): `import-source` is a multimethod on the source's `:kind` returning a seq of `{:recipe <parse-form-shaped map> :image {:bytes} :warnings [...]}` (or `{:failed "why"}` for one recipe of a multi-recipe source); `core/save!` fits the recipe to the editor's limits (`fit`), stores the image through `images/store!` (a failed image is a warning) and creates it published, so lines go through the parser and matcher. `:web` fetches the page, reads schema.org Recipe from JSON-LD (anywhere in the JSON, incl. `@graph`; invalid blocks skipped) then microdata (props of nested items ignored), and maps name, description (HTML stripped), image (string/ImageObject/list, resolved against the page), recipeYield (first integer), prep/cook/total ISO 8601 durations (cook = total − prep when missing), recipeIngredient and recipeInstructions (text, HowToStep, HowToSection). Other sites' ratings and keywords are not imported. Without recipe data the Add page shows the error and offers the blank editor with the address as the source. `:tandoor` reads an uploaded export (`{:kind :tandoor :file File}`): a zip of numbered zips (sorted numerically), each with `recipe.json` and maybe `image.<ext>`, or one recipe's zip. Everything read is capped (inner zip 20 MB, recipe.json 2 MB, image `images/max-bytes`, 5000 recipes); an unreadable inner zip becomes a `:failed` item. It maps name, description, servings, working/waiting time → prep/cook (0 → unknown), source URL, keywords → tags, steps (named steps put their name on its own line) and ingredients rebuilt as text (`ingredient-line`: amount via `format-qty`, unit, food, `, note`; without an amount the unit goes in parentheses after the food so the name still matches; no-amount drops the unit; headers skipped; empty `()` left by Tandoor's parser removed). The Add page's Import from Tandoor card uploads with `data-upload-kind="tandoor"` (500 MB) and posts to `/api/recipes/import/tandoor`; `pages.recipes/import-all!` saves each recipe, skipping titles already in Larder (`recipes/title-keys`) when Skip is checked, and the card lists imported (links, warnings), skipped and failed recipes.

**Images** (`images.clj`): every image is decoded with ImageIO (JPEG, PNG, GIF, BMP; dimensions checked from the header, max 50 megapixels; file max 10 MB), flattened onto white, scaled to at most 2000 px on the longest side and re-encoded as JPEG into `<data-root>/media/<32 hex>.jpg`. `GET /media/:file` serves it as `image/jpeg` only when a recipe uses it: published recipes for everyone, drafts for signed-in users. Replacing or removing an image, or deleting the recipe, deletes the file. Phase 4's downloaded images go through `images/store!` too.

**UI rendering**: server-side Hiccup + htmx. `pages/layout.clj` is the app shell: header (site name, username, public dashboard, settings, log out) and sidebar (Add, then Recipes, Meal plan, Pantry, Grocery). Pages return `(layout/main section ...)` — SECTION is the sidebar key to highlight — and `layout/app-page` wraps it (htmx navigation requests get only `#main`). In-app links use `ui/nav-attrs` so only `#main` is swapped and the URL is pushed; `main.js` moves the sidebar highlight to `#main`'s `data-section` after each swap. On phones (≤768px) the sidebar and the page take turns: `body.nav-open` shows the sidebar full width and hides `#main`; a full load of plain `/app` starts with it (`layout/start-with-nav?`), the header's menu button (`data-toggle-nav`, phones only) toggles it, and any swap of `#main` clears it. `pages/public.clj` renders the public dashboard with header tabs (Recipes; Grocery list joins in Phase 6 when access is Open) beside Log in. `ui.clj` holds icons and form helpers (`field`, `select`, `alert`, `tabs`, `copy-field`). htmx is vendored in `resources/public/js/vendor/`; `main.js` has copy buttons, themed `hx-confirm`/`data-prompt` dialogs (`bsDialog`) and the sidebar highlight. Styles are Block Shipper's `theme.css`/`main.css`/`login.css` copied as is, with Larder additions at the end of `main.css`. Response helpers in `response.clj`: `h-respond` for Hiccup, `respond` for HTML strings, `respond-generic` for other content types.

**Passwords**: Argon2id via `buddy-hashers`, Base64-encoded before storage.

## DB Schema

All tables are single-tenant (no household or owner column). Recipes, their lines and tags, ingredients and aliases are an index of the library files (see Library), rebuilt from them at startup. Times are epoch milliseconds. `migration.clj` holds idempotent statements that all run whenever `server-version` changes; add new ones at the end (`create table if not exists`, `alter table ... add column`, or a var of a function of the db-spec that checks before it writes, like `seed-ingredients!`). The SQLite connection enables `foreign_keys`.

`db_version`, `users` (role `admin`|`user`, `enabled`), `sessions` (`sid`, `session_obj`, `created_at`), `global_settings` (`key`, `value`).

0.2.0: `recipes` (title, description, servings, prep/cook minutes, steps as text with one step per line, source_url, status `draft`|`published`, image_path, rating 1-5 or null, created_by, created_at, modified_at), `recipe_ingredients` (recipe_id, position, ingredient_id/quantity/unit/note — null until Phase 3 — and original_text), `recipe_tags` (recipe_id, tag). Children cascade on recipe delete.

0.3.0: `ingredients` (name unique nocase, dimension, density, default_quantity, default_unit, always_have, created_at, modified_at), `ingredient_aliases` (ingredient_id, alias unique nocase), index on `recipe_ingredients.ingredient_id`; seed set.

0.5.0: `pantry_items` (ingredient_id cascade, quantity, unit, added_at, source, added_by). `db/insert!` returns a new row's id. (Version numbers follow the phase that added the tables.)

0.6.0: `stores` (name unique nocase, notes), `grocery_items` (section, ingredient_id cascade, text, quantity, unit, store_id set null, origin, added_by, added_at, done_at, purchased_quantity, purchased_unit, pantry_item_id).

0.8.0: `cook_log` (recipe_id set null on delete, meal_plan_entry_id, servings, user_id, cooked_at).

0.9.0: `meal_plan_entries` (date text, recipe_id cascade, servings, position, cooked_at).

0.10.0: `api_keys` (user_id cascade, name, key_id unique, key_hash, last_used_at, created_at, revoked_at).

0.11.0: `oauth_clients` (client_id unique, kind registered|metadata, name, redirect_uris JSON, created_at, fetched_at), `oauth_codes` (code_hash, client_id, user_id, code_challenge, redirect_uri, resource, scope, family, expires_at, used_at), `oauth_tokens` (access_hash, refresh_hash, client_id, user_id, resource, scope, family, access/refresh expiry, created_at, last_used_at, revoked_at).
